## How the footage was made

- **Dedicated database.** `loandocket_explainer` was migrated and seeded with the standard sample users (`pnpm db:migrate`, `pnpm db:seed`). The working `acqfile` database is never used.
- **Dedicated deal.** `scripts/prepare-deal.ts <CODE>` creates a new deal from the D08 demo-case profile and files, through the same service calls as `pnpm demo:cases seed` (`saveDeal`, `intake`, `processDealRun`). It refuses a code that already exists.
  - Three files are held back so they can be uploaded on camera: the D08 round-2 amended purchase agreement ($1,050,000), Kiel McDermott's August statement and Jaylan Heller's 2025 return.
  - Kiel McDermott's 2025 return is never supplied, so it stays missing.
  - Nothing is reviewed, answered, accepted or waived off camera.
- **Recording.** `scripts/record.mjs` drives Chromium through Playwright as the Operator (`reviewer@example.com`). The password is read from `.env.local` and never printed. Every demonstrated decision is a UI action on the normal screens:
  - upload, filter, overview and review;
  - the amended agreement opened from the Review card, and its values beside the source page;
  - "Record an answer" on the Review card, which opens the existing question page;
  - Review showing the saved answer, and the answer reopened;
  - editing and copying the Follow-ups draft (Record as sent is never pressed, and nothing is sent);
  - creating the lender-file version and downloading the ZIP;
  - opening the report from the downloaded ZIP.
- **Capture resolution.** Playwright's built-in video ignores `deviceScaleFactor`. So the page is laid out at 1440×810 CSS pixels under a 2× CSS zoom in a 2880×1620 viewport, and captured through the DevTools screencast (`scripts/recorder.mjs`). The cursor is an overlay that follows the real mouse events.
- **Readings.** `LLM_PROVIDER=mock`, so document readings come from the committed prepared candidates for these synthetic files. The README and the How it works page say so beside the video. Real PDF parsing still runs.

### Checks the recorder makes

`record.mjs` stops with an error, and writes no `take.json`, if any of these fails.

**Before anything changes:**

- The app URL is explicit and local (`EXPLAINER_BASE_URL`; there is no default port).
- The database URL is the local `loandocket_explainer` (`EXPLAINER_DATABASE_URL`).
- The deal is in "LoanDocket Demo Workspace" and has the expected name.
- The signed-in account has the reviewer (Operator) role.
- The deal is fresh: no versions, no answers, and none of the on-camera files uploaded.
- `work/upload` holds exactly the three on-camera files.
- The running app serves that deal's id and code, which proves it uses the same database, and shows "Synthetic data only".

**After each action:**

- The document page explains the price disagreement and does not claim the documents are absent.
- The preferred price and reason are saved (database and Review).
- The disagreement is still open.
- The answer persists when reopened.
- The edited draft is exactly the expected complete text.
- "Copy draft" copied exactly that text.
- The download completed and is a valid ZIP named for the deal.
- The deal has exactly one version, matching the download.
- `inspect-package.mjs` passes on that ZIP (next section).

**Take safety:**

- Take names must be 1–48 of `a-z 0-9 - _` and resolve directly under `work/`.
- An existing take is never cleared. The recorder refuses it unless `--overwrite` is given, and then moves it aside to `<take>.replaced-<time>`.
- Without `--take`, a fresh `take-<timestamp>` name is used.

## Reproduce

Run from the repository root. Needs Node 22+, PostgreSQL 17 client tools, ffmpeg and macOS `say`. Uses the existing `.env.local` in sample mode (`REAL_DATA_MODE=false`, `ACQFILE_SAMPLE_MODE=true`, `LLM_PROVIDER=mock`). The fonts are committed in `fonts/`; no preparation step is needed.

```sh
# 1. Dedicated database and users (one time)
createdb loandocket_explainer
export DATABASE_URL=postgres://localhost:5432/loandocket_explainer LOCAL_STORAGE_DIR=.data/explainer-storage
corepack pnpm db:migrate && corepack pnpm db:seed

# 2. A new deal for each take (a take consumes its deal: the upload, answer and version are real)
corepack pnpm exec tsx artifacts/loandocket-explainer/scripts/prepare-deal.ts VCS-2026-016

# 3. App on the dedicated database, on a port of your choice (not the e2e ports 3100/3104)
corepack pnpm exec next dev -p 3200      # keep running, same DATABASE_URL/LOCAL_STORAGE_DIR

# 4. Record (checks run as it goes; see above)
EXPLAINER_BASE_URL=http://localhost:3200 \
EXPLAINER_DATABASE_URL=postgres://localhost:5432/loandocket_explainer \
  node artifacts/loandocket-explainer/scripts/record.mjs --deal VCS-2026-016 --take r3-clean

# 5. Point scripts/edit.json at the take: "take", and "expect" (deal code, name, package version)

# 6. Cards, a voice set, then validate and render. edit.json names the Gemini Iapetus set (see "Current voice");
#    narrate.sh makes the earlier Samantha set instead. A full render with either voice needs its timing rechecked
node artifacts/loandocket-explainer/scripts/cards.mjs
sh artifacts/loandocket-explainer/scripts/narrate.sh
python3 artifacts/loandocket-explainer/scripts/render.py --check       # validate only
python3 artifacts/loandocket-explainer/scripts/render.py               # render, check, then publish
```

### What `render.py` guarantees

- **Take-specific intermediates.** Everything is built under `work/render/<take>/`. The master video carries a key made from the take name, the take's `timeline.json` hash and the conversion settings. It is rebuilt whenever any of these differ, so one take's footage can never be used for another. Shot clips are rebuilt on every run.
- **Preflight** (nothing is rendered if any check fails):
  - **Take:** has `take.json`, a timeline, and every frame file. Its deal code, deal name and package version match `edit.json` `expect`. The retained ZIP exists, its hash matches `take.json`, its report heading names the deal and version, and its inspection passed.
  - **Shots:** every marker exists. Ranges are not empty, reversed, negative or past the end of the footage, and crops stay inside the layout.
  - **Fonts, cards and audio:** fonts are present. Cards are present and generated from the current `edit.json`, `narration.json`, fonts and `cards.mjs`, checked by input hash. Every cue has audio generated from its current text, checked by text hash.
  - **Timing:** narration cues are at least 0.25 s apart and the last ends 0.3 s before the video. Captions do not overlap, do not disappear before their narration ends, and stay inside the video. The total is within 75–90 s.
  - Planned timing is checked again with the actual rendered clip lengths.
- **Post-render checks on the file:** duration and range; H.264 High 1920×1080 at 30/1; AAC 48 kHz lasting the whole video; one caption track; frame count; no black frames (`blackdetect`); audible audio (`volumedetect`). Still stretches of 4 s or more are listed for review.
- **Publishing:** the video is rendered to `work/render/<take>/final.tmp.mp4`. Only after every check passes is it moved over `loandocket-explainer.mp4`, with `captions.srt` likewise. `--no-publish` stops before that, which is useful for rehearsals.

### Timing: when to check and when to retime

Shot in and out points are recording markers plus offsets (`scripts/edit.json`), and caption cues start `at` seconds into a shot. So a new take usually lines up without edits. It is **not guaranteed**. Shot lengths come from the recording itself and change when any of these change:

- processing time (upload, version creation, download);
- page load and render time;
- scroll positions;
- the pacing in `record.mjs`.

Narration length changes with the voice or the text. Always run `render.py --check` after a new take, a new voice set, or any change to `narration.json` or `edit.json`. It prints the planned timeline and fails on overlaps, cut-off narration or an out-of-range total. Also look at the frames of any shot whose length changed: crops are fixed rectangles, so a different scroll position can leave the subject outside the crop. `scripts/frames-at.py work/<take> <marker>+<sec>` prints the frame at a marker.

Retiming means editing only `edit.json`: a shot's `from`/`to`, a `hold` to extend a still, the opening or closing `duration`, or a cue's `at`. The footage is not re-recorded.

### Replacing the voice in a full render

The recorded footage does not depend on the voice. To render the whole video again with another voice:

1. Generate one WAV per cue into `work/audio/<new-set>/` from the `text` of each cue in `narration.json`. The set name may contain only lowercase letters, digits, `-` and `_`; `render.py` refuses any other.
2. Write `work/audio/<new-set>/manifest.json` in the same shape as `narrate.sh` writes: `{"tool", "voice", "cues": {"n1": {"file": "n1.wav", "text_sha256": "<sha256 of the cue text>", "duration": …}, …}}`.
3. Run `python3 artifacts/loandocket-explainer/scripts/render.py --voice <new-set> --check`. Adjust cue `at` values, holds or card durations in `edit.json` until it passes. Then set `"voice"` in `edit.json` and render.
4. Listen to the whole result. Check pronunciation (LoanDocket, McDermott, Heller, Varnholt, the dollar amounts), pacing and the agreement with the screen. Then update `narration.md` and this README.

If a new voice reads "LoanDocket" correctly as written, the cue `text` can change. The audio must then be regenerated, and the text-hash check enforces this.
