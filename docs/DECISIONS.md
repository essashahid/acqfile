## Specification contradictions and gaps

- Section 1 says seven phases, while Section 23 enumerates eight (0 through 7). Follow the explicit table and the user's phase boundary.
- Synthetic-only is a hard guardrail, while Phase 7 asks for a paid-pilot runbook using clients' past files and REAL_DATA_MODE. Keep real data disabled; the runbook must describe a future separately authorized operational transition, not enable it under this specification.
- Section 15 names every packaged source `.pdf`, but intake includes DOCX/XLSX and originals must remain unchanged. Preserve original extensions/bytes; use PDFs for generated reports. Do not disguise non-PDF bytes with a PDF extension.
- CON-16 lists `needs_review` as severity although the severity enum permits blocker/major/minor/info. Treat it as finding type `needs_review`, with severity to be explicitly configured (planned: major).
- GUA-05 sits under per-guarantor items but explicitly requires every direct/indirect owner and guarantor. Its scope must be the union of those parties, not only guarantors.
- TXN-05 requires Form 155, while the taxonomy lacks it; other composite items lack explicit types (donor/transfer evidence, franchise disclosure, appraisal/environmental tracking). Resolve with sourced taxonomy/config entries or tracking/manual evidence, never silently count unrelated documents.
- TXN-07 depends on paid-agent compensation, and several checks depend on cash contributions, account history, guarantor spouses, leases and transaction details absent from the stated profile/field lists. Add explicit validated data fields in the relevant future phase or yield needs_review.
- Classification-only CREDIT_AUTH requires a signature check; RECEIVED alone cannot prove this. Shared segment signature metadata/manual confirmation must supply the check.
- CON-07's combined limited-source rule is described as an 8.1 change but has no pack qualifier in the consistency table. Scope it to sourced pack versions; do not impose an unsourced 8.1 rule on pack 8.
- YAML arithmetic examples use infix strings while the stack asks for JSON-logic style conditions and no eval. Normalize into a small validated expression representation; reject unknown operations. Do not execute arbitrary expressions.
- "Every exported file ends with" the footer conflicts with immutable original copies/binary ZIPs. Put the exact footer in generated document/sheet outputs and package manifest metadata; never modify supplied originals.
- Manual confidence 1.0 must not bypass required locator, actor, validation or review invariants.
- The two live model identifiers in the base are identical. This conflicts with independent verification and is corrected in Phase 0.

87. A rule-consumed attribute whose sole producer is the segment's type is expected of every such document; a null becomes an `extraction_gap` review item without a fact. That is how a planted missing value routes to review without any hand list.
88. A39 cross-pass agreement compares the extractor's value with the verifier's independent corrected value after normalization; a verifier-corrected fault therefore scores 0.70, not 0.85, and the two fault descriptions were corrected before the proof ran. Scores are rounded to four decimals; routing precedence is unknown locator, unsupported evidence, verifier unsupported, contradiction, below review, vision, below auto-accept.
89. Extraction steps are durable per segment: the segment id is a scope suffix on the idempotency key, so a bundle's segments get their own `extract` through `finalize_segment` rows and a completed step is never repeated or re-billed. After an operator confirms or re-files segments, a `reprocess` run reuses the parse step and reads the confirmed segments; facts of replaced segments stop being current.
90. A40 on images: a model-read identifier is never stored. It raises an `extraction_gap` entry item carrying the last four so the operator enters the full identifier from the original and code stores the HMAC; a last-four mismatch with the assigned party raises `identifier_mismatch`.
91. The mock extractor and verifier answer from `documents.json` keyed by file hash and segment start page, cite the runtime block that contains the truth quote, and follow planted faults; the live provider uses the Responses API with strict JSON output and the verifier on a different model. Both return values as JSON-encoded strings so one strict schema serves every value type.
92. Underlying step errors are printed to the console only when `ACQFILE_DEBUG` is set; persisted run events keep the generic message so source text never reaches logs.
93. The grouped review screen lives per segment. Accept, edit and accept, reject and needs-a-better-copy each write a new immutable `facts` row (record version plus one, reviewer, old and new value, comment and time in an audit event) and reject a stale expected version; an edited value becomes a `manual` fact with the operator as actor (A14). Reclassify opens a classification item and sends the operator to the filing screen; re-filing supersedes the old segment's facts.
94. Extraction gaps and image-read identifiers are resolved on the same screen: the operator enters the value from the page (a manual fact citing the page, quote marked not verbatim) or records that the document does not state it.
95. Entity resolution matches an owner row by identifier HMAC first and otherwise by an exact normalized name against legal names and variants; a unique match becomes an `ownership_links` row with origin `extracted`, anything else raises `party_assignment`. The unique key on ownership links now includes origin, a profile save replaces only declared links, and the engine input takes declared links over extracted links with the same identity.
96. The engine input is built from current rows only: confirmed current segments, current facts that are accepted (auto-accepted or accepted) as accepted facts and review, blocked or needs-source facts as pending facts, rejected facts excluded, attestations for tracking, manual confirmations and waivers, and an evidence inventory of exactly those ids. Every fact carries its document's period, as the fixture truth does. Evaluations, checklist rows and findings are persisted; findings upsert on their key and keep their first-seen evaluation; the deal page shows counts only.
97. Evaluation requests coalesce per deal: a request during a running evaluation schedules exactly one follow-up. Filing, operator review, extraction after review, a completed batch run and a profile save all request an evaluation and await it in the inline job driver.
98. Operator attestations (tracking state, manual confirmation, waiver) get a table and an audited API in this phase because the engine reads them; their screens are Phase 5. The proofs record the plan's authored attestations through that API.
99. A42 removed the legacy corpus, report schema, extraction path, review queue, dashboards, evaluation cases and their tables in migration 0012; `record_versions` stays for filing records without its extraction columns. `pnpm eval` runs the Phase 3 and Phase 4 proofs until Phase 6.
